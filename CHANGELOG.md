## 2026-07-21 — Planeación completa (Ideación → Planeación → Estrategia → Ejecución)

- Definido el objetivo: app personal de finanzas (ingresos, gastos, deudas por medio de pago, metas) sincronizada entre PC y Android, con módulo de tiempo/IA en fases futuras.

Protección por API key fija, sin login. Adaptador MCP para IA planeado pero diferido hasta tener el CRUD base sólido.

- Creados `CLAUDE.md` (documentación viva del proyecto) y este `CHANGELOG.md`.
- Acordado el modo de trabajo: avances fragmentados con checkpoints, cada avance documentado aquí, diseño de frontend distintivo (skill `frontend-design`), y las carpetas `frontend/`/`backend/` las crea Nico.

## 2026-08-25 — Adaptador Postgres real para `TransactionRepository`

- Conexión a Supabase configurada vía variable de entorno `DB_CONNECTOR` en `back_finanzas/.env` (no versionado), leída por `infrastructure/db/config.py` con `pydantic-settings`.
- Creado `infrastructure/db/session.py`: `engine` de SQLAlchemy (conexión real a Postgres) y `SessionLocal` (fábrica de sesiones), más `get_db()` como generador (`yield` + `finally`) para entregar una sesión y garantizar su cierre — patrón que más adelante usará FastAPI vía `Depends`.
- Creado `infrastructure/db/base.py` (`declarative_base()`) y `infrastructure/db/models.py` con `TransactionModel`, el mapeo ORM de la entidad `Transaction` a la tabla `transactions`. Usa el estilo tipado moderno de SQLAlchemy 2.0 (`Mapped[...]` + `mapped_column()`) en vez del `Column()` clásico, porque este último no tipa correctamente los atributos de instancia (`model.id` aparecía como `Column[int]` en vez de `int` para el chequeo estático de Pylance).
- Decisión de diseño: los `Enum` del dominio (`TransactionType`, `Method`, `Category`) se guardan como `String` plano (su `.value` en español, ej. `"gasto"`), no como tipo `ENUM` nativo de Postgres — se prioriza poder agregar valores nuevos sin necesitar una migración de esquema, sobre la validación extra a nivel de base de datos (que de todas formas ya cubre el dominio).
- Tabla `transactions` creada en la Supabase real vía `Base.metadata.create_all(engine)`, y verificada con `sqlalchemy.inspect` contra la base de datos real.
- Creado `infrastructure/db/postgres_transaction_repository.py`: `PostgresTransactionRepository`, implementación real del puerto `TransactionRepository` — recibe una `Session` por inyección (no la crea ella misma), convierte el `Transaction` de dominio a `TransactionModel` (traduciendo los Enums a `.value`), guarda con `add`/`commit`/`refresh`, y devuelve el `Transaction` con el `id` real asignado por Postgres.
- Probado end-to-end contra la Supabase real (no un fake): se guardó una transacción de prueba y se confirmó su persistencia en la tabla.

## 2026-08-25 — Primer endpoint FastAPI: `POST /transactions`

- Protección por API key fija (`API_KEY` en `.env`, distinta de `DB_CONNECTOR`): `infrastructure/api/config.py` (misma base de `pydantic-settings` que la config de DB; se agregó `extra="ignore"` en ambas configs porque comparten un mismo `.env` y cada una solo declara sus propios campos) e `infrastructure/api/auth.py` con `verify_api_key`, una dependencia de FastAPI que valida el header `X-API-Key` contra la key configurada y responde `401` si no coincide.
- Creados los DTOs en `infrastructure/api/schemas.py` (`TransactionBase`, `TransactionCreate`, `TransactionResponse`) — contrato HTTP separado de la entidad de dominio `Transaction`, reutilizando directamente los `Enum` del dominio (Pydantic los valida solo). `TransactionResponse` usa `model_config = ConfigDict(from_attributes=True)` para poder construirse a partir del objeto de dominio devuelto por el caso de uso, no solo de un dict.
- Creada la app FastAPI (`infrastructure/api/main.py`) y el router (`infrastructure/api/routes.py`) con el endpoint `POST /transactions`: valida la API key, obtiene una sesión de DB vía `Depends(get_db)`, arma `PostgresTransactionRepository` + `RegisterTransaction`, ejecuta el caso de uso, y traduce las excepciones de dominio (`DomainError`) a `HTTPException(422)` con el mensaje original.
- Probado end-to-end (sin key → `401`, key incorrecta → `401`, key correcta → `200` con la transacción guardada en la Supabase real).

## 2026-08-27 — Listado de transacciones: caso de uso `ListTransactions` y endpoint `GET /transactions`

- Creado el caso de uso `ListTransactions` (`application/use_cases/list_transactions.py`): a diferencia de `RegisterTransaction`, no construye ni valida nada, solo delega en el puerto — es el caso de uso más simple de los dos que existen hasta ahora.

A diferencia del `POST`, no tiene `try/except` porque `ListTransactions` no puede lanzar `DomainError` (no recibe ni valida datos del usuario) — se evitó agregar manejo de errores para un escenario que hoy no puede ocurrir.

## 2026-08-27 — Fetch de una transacción por id: caso de uso `GetById` y endpoint `GET /transactions/{id}`

- Agregado el método abstracto `get_by_id` al puerto `TransactionRepository`, devolviendo `Optional[Transaction]` — a diferencia de `save`/`list_all`, este método puede no encontrar nada, así que el tipo de retorno lo refleja explícitamente.
- Implementado en `InMemoryTransactionRepository`: busca en la lista interna la transacción cuyo `.id` coincide (`next(..., None)`), en vez de tratar el `id` como índice de posición — el primer intento tenía ese bug (`self._transactions[id]`), corregido antes de mergear.
- Implementado en `PostgresTransactionRepository` usando `self._session.get(TransactionModel, id)` — consulta directa por clave primaria, sin traer toda la tabla a memoria (el primer intento hacía `.query(...).all()` y buscaba en Python, ineficiente); devuelve `None` explícitamente antes de construir el `Transaction` de dominio si no hay match, evitando un `AttributeError` sobre `None`.
- Creado el caso de uso `GetById` (`application/use_cases/get_by_id.py`), mismo patrón que los anteriores: delega en el puerto, sin construir ni validar nada.
- Creada la suite `tests/application/use_cases/test_list_by_id.py`, con dos tests: transacción existente devuelve todos sus datos correctos, transacción inexistente devuelve `None`.
- Agregado el endpoint `GET /transactions/{id}` en `routes.py`: a diferencia de los otros dos endpoints, no traduce una excepción del dominio sino un valor `None` — cuando `GetById.execute()` no encuentra la transacción, el endpoint lo traduce a `HTTPException(404)` explícitamente con un `if`, no con `try/except` (no hay ninguna excepción real que atrapar en ese flujo).
- Probado end-to-end contra la Supabase real (id existente → `200` con los datos, id inexistente → `404`, sin key/key incorrecta → `401`).
- Con esto queda completo el CRUD de lectura de `Transaction` (crear, listar todas, obtener una por id); quedan pendientes `PUT`/`PATCH` (editar) y `DELETE` para cerrar el CRUD completo.

## 2026-08-28 — Eliminar transacción: caso de uso `RemoveTransaction` y endpoint `DELETE /transactions/{id}`

- Agregado el método abstracto `remove(self, id: int) -> bool` al puerto `TransactionRepository` — devuelve `True` si se borró algo, `False` si no existía, en vez de lanzar una excepción, siguiendo el mismo criterio de `get_by_id` (que devuelve `None` en vez de lanzar).
- Implementado en `InMemoryTransactionRepository`: busca la transacción por `id` con el mismo patrón que `get_by_id` y, si existe, la remueve de la lista interna.
- Implementado en `PostgresTransactionRepository` usando `session.get` + `session.delete` + `commit`, mismo estilo de búsqueda que `get_by_id`.
- Creado el caso de uso `RemoveTransaction` (`application/use_cases/remove_transaction.py`), mismo patrón simple que `GetById`/`ListTransactions`: delega en el puerto sin lógica propia.
- Creada la suite `tests/application/use_cases/test_remove_transaction.py`, escrita antes de implementar el adaptador Postgres (a diferencia de las piezas anteriores) porque los tests del caso de uso dependen solo del fake, no de Postgres. Cubre transacción existente (devuelve `True`, y `list_all()` queda vacío) y transacción inexistente (devuelve `False`).
- Agregado el endpoint `DELETE /transactions/{id}` en `routes.py`, protegido por API key, sin `response_model` y con `status_code=204` (sin cuerpo de respuesta, convención estándar para `DELETE`) — traduce el `False` del caso de uso a `HTTPException(404)`, igual que hace `GET /transactions/{id}` con `None`.
- Renombrado el endpoint `get_by_id` a `get_transaction_by_id` en `routes.py` para evitar confusión con los nombres de los demás endpoints de la ruta.
- Con esto queda completo el CRUD de `Transaction` salvo editar (`PUT`/`PATCH`), la única pieza pendiente para cerrar la fase 2 del roadmap.

## 2026-08-29 — Editar transacción: caso de uso `UpdateTransaction` y endpoint `PUT /transactions/{id}`

- Agregado el método abstracto `update(self, id: int, transaction: Transaction) -> Optional[Transaction]` al puerto `TransactionRepository` — devuelve la transacción actualizada, o `None` si el `id` no existe, mismo criterio que `get_by_id`.
- Implementado en `InMemoryTransactionRepository`: busca la transacción por `id` con el mismo patrón que `get_by_id`/`remove` y, si existe, sobreescribe sus campos en el sitio.
- Implementado en `PostgresTransactionRepository`: busca el `TransactionModel` por `id`, sobreescribe sus campos (traduciendo los Enums de dominio a `.value`, igual que `save`), hace `commit`/`refresh`, y reconstruye el `Transaction` de dominio actualizado para devolverlo. El primer intento tenía un bug (`self._session.get(Transaction, id)`, usando la entidad de dominio en vez de `TransactionModel`) y creaba un `TransactionModel` intermedio innecesario solo para copiar sus atributos — ambos corregidos antes de mergear.
- Creado el caso de uso `UpdateTransaction` (`application/use_cases/update_transaction.py`): construye una `Transaction` de dominio con los datos nuevos (delegando la validación al dominio, mismo patrón que `RegisterTransaction`) y la persiste a través del puerto.
- Creada la suite `tests/application/use_cases/test_update_transaction.py`, con dos tests: transacción existente se actualiza y devuelve los nuevos datos, transacción inexistente devuelve `None`.
- Agregado el endpoint `PUT /transactions/{id}` en `routes.py`, reutilizando `TransactionCreate` como body (mismos campos obligatorios que necesita `UpdateTransaction`, sin necesidad de un schema nuevo): traduce `DomainError` a `HTTPException(422)` igual que `POST /transactions`, y `None` a `HTTPException(404)` igual que `GET /transactions/{id}`/`DELETE /transactions/{id}` — es el primer endpoint que combina ambos tipos de traducción de error.
- Escrito por Nico con guía paso a paso de Claude; Claude escribió directamente el bloque `try/except DomainError` del endpoint a pedido explícito de Nico, y el `raise HTTPException(404, ...)` correspondiente.
- Con esto queda completo el CRUD de `Transaction` (crear, listar, obtener por id, editar, borrar), cerrando la fase 2 del roadmap. Pendiente probarlo end-to-end contra la Supabase real.
- Probado por Nico end-to-end contra la Supabase real: `PUT /transactions/{id}` funciona correctamente.

## 2026-08-29 — Decisión de alcance: Fase 2 cerrada solo con `Transaction`, `Deuda` diferida

- Definido que el balance de la app se calcula como la suma de todas las `Transaction` (ingresos suman, gastos restan), arrancando en 0 y fluctuando en positivo/negativo — esto es todo lo que se necesita del backend para ese comportamiento, así que la entidad `Deuda` (mencionada en la arquitectura junto a `Transacción` y `Meta`) no es necesaria para cerrar la Fase 2.
- Decisión: `Deuda` se difiere, no se elimina del roadmap. Se retoma más adelante si surge necesidad real de trackear una obligación pendiente (a quién se le debe, si está pagada) como algo distinto de un gasto puntual — por ejemplo al construir el dashboard de la Fase 4, si ese caso de uso lo pide.
- `CLAUDE.md` actualizado: Fase 2 del roadmap redefinida como "ingresos y gastos por medio de pago (entidad `Transaction`)" y marcada completa; Fase 4 ya no menciona "deudas próximas" en su alcance actual.
- Con la Fase 2 cerrada, el siguiente paso del roadmap es la Fase 3: frontend Expo (pantallas de registro y listado de transacciones, conectadas al backend).

## 2026-08-29 — Diseño del modelo `Deuda` (sin implementar)

Ahora en colapsado el botón tiene un tamaño fijo 44×44 centrado (`alignItems: "center"` en el contenedor), y en expandido sigue estirándose a todo el ancho como antes.

No era un problema de tipografía; el `lineHeight`/`marginTop` del intento anterior se revirtió.
